# C25-05 儲存方案比較（2026-10-11；設計阻擋，非定案）

**目標與證據。** GW 的 `SaveStatusAsync` 必須在成功回覆前完成持久化，且 Aster 不接受移除 `Flush(true)`／atomic rename。於 PTC source commit `075682ef315cc6823217a6adccaad6fecac00c48`，`G:/PulseTrade.fs/Libs/PulseTrade.Comm/src/PulseTrade.Comm.GW.Host/GatewayPcslStores.fs:407-428` 先呼叫 `appendStatusCore`，再更新記憶體 latest map；前者在同檔 `298-315` 對 `[all; ticket]` 做一次 append，另於 `275-283` 對 bucket 做一次 append。暖機後兩者均走 `appendKnownSetValue` (`85-101`)：**每次 Save 有兩次同步 backend `Append` 呼叫，不是單一原子交易**。`PulseTrade.Comm.Spa` 套件內每次 Append 實際做幾個 `.val` 提交／`Flush(true)`，目前沒有 source-level 計數；不可把 process I/O counter 當 fsync 次數。固定 GW 快照 200 次 Save 的 v8 DLL SHA `45E85B90FBC118AB12644E9FCE26DEED25154E098AC8B227913D5B545695AA33` process counters 為 800 write operations／1600 read operations，即每 Save 平均 4／8；401 為 1200／800，即 6／4。這是觀測值，不是 durability syscall 數。v8 對**每個既有小 `.val`** 的 native 路徑確實執行一次 temp `Flush(true)` 加 rename（`ChunkedValue.fs:123-132,500-532`）。

| 方案 | ACK 前的最少工作與延遲預期 | crash recovery／compaction 成本 |
|---|---|---|
| 現行 v8：每值原子替換 | 兩個 backend Append 依序返回；每個命中的既有小值做 flush＋rename。隔離 GW 同快照 ABBA p50 17.061／14.072ms、CPU 4750／4422ms，401 p50 9.072／9.919ms、CPU 3422／3281ms；正式 gate FAIL。 | 沿現行 PCSL recovery；兩次 Append 間仍可能只有前一次落盤，需依既有 retry/index reconciliation 處理。無新增 compactor。 |
| 在既有兩次 PCSL Append 外層排隊／group commit | **不能**只把兩個呼叫併在同一鎖就減少 flush。若要一次 flush 涵蓋一個或多個 Save，須先有可持久化的共同 commit record，等待該 record flush 後才 ACK；跨請求湊批會增加等候時間，並改變目前同步 lock 的併發路徑。需實測 GW 負載，不能推定更快。 | 需要有序 sequence、已提交邊界、重啟 replay 與 idempotent status/index 投影；bounded queue/backpressure、checkpoint 與舊批次回收。屬 GW/backend contract 變更。 |
| append-only WAL＋非同步 PCSL projection | 把 status 與 bucket 更新包成**一筆**帶長度／checksum 的 commit record，flush WAL 後才 ACK；PCSL projection 可落後，但 read/latest 必須涵蓋已 ACK WAL。單請求仍至少一次 durable flush；若要跨請求 group flush，須新增受控批次等待。 | 冷啟動掃 WAL 到最後完整記錄、重播未投影 sequence、去重並核對 index；需要 epoch/checkpoint、檔案輪替／compaction、容量上限與磁碟滿／部分尾端處理。若沒有這些，不能替換現行方案。 |

**判定。** `File.Replace` 與 WriteThrough＋Flush 在本機原語對照比現行 Move 更慢（[SD](SD.md)）；沒有已證明能保留安全語意又關閉 GW 差距的小修。group commit/WAL 會改 GW 持久化、讀取及恢復契約，須由 GW owner 定 API/ACK/read 一致性後建候選，再用同 ZIP SHA `3CB5FB6AA7836E066E11DBA08462B8F1C14D64343A16894A8D7AA6F917520E35`、ABBA、2293 筆 cold digest、native safety suite 和正式 Host 負載驗收。v8 保持 development source；不 package／deploy。實測方法與限制見 [TEST_Feedback](TEST_Feedback.md)。
